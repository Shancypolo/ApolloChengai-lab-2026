# PageOne technical handoff

## Document control

Owner: the local app maintainer. Review this document whenever a prompt, model, input context, source domain, URL behavior, output shape, storage field, dependency, visual asset, diagnostic, or test changes. Facts below describe the current code; product choices and limitations are called out as assumptions. Last reviewed: 2026-11-04.

PageOne is a finished local, single-user loopback app. It has no login, remote deployment, database server, job queue, multi-process lock, or service monitoring. One Flask process owns the jobs, archive lock, and usage meter. Restarting it stops active jobs and clears in-memory session usage; saved archive data remains on disk. The supported `run.py` command can serve a static local failure page even when Flask or another required package is missing.

## Setup and run

Python 3.10 or newer is required. In this directory, install dependencies directly and start the app:

```sh
python -m pip install -r requirements.txt
python run.py
```

A virtual environment is optional. It is a private folder for this app's installed Python packages, so the install does not affect other projects. To use one, run `python -m venv .venv` and activate it with `.venv\Scripts\Activate.ps1` on Windows PowerShell or `source .venv/bin/activate` on macOS/Linux before installing.

Set `OPENAI_API_KEY` in the active terminal; keep it out of source control. Start with `python run.py` and open `http://127.0.0.1:5000`. The app binds to loopback only. It does not load `.env` files. Set `PAGEONE_PORT` to use another local port; `PAGEONE_DATA_DIR` changes the local folder for the archive and log, which otherwise live under `user data/` beside `app.py`.

For offline and browser checks, install `requirements-dev.txt`; `tests/startup_smoke.py` also checks the missing-package notice using standard-library Python; Playwright may need a one-time Chromium install with `python -m playwright install chromium`. `tests/visual_test.py` can also use an installed `chromium` executable.

The application uses Python, HTML/Jinja2, CSS, and two local JavaScript files; there is no HTMX asset, third-party script, or JavaScript package dependency. `reading_position.js` only keeps a clicked summary heading visually steady during the native `<details>` layout change. `local_requests.js` intercepts same-origin forms and ordinary same-origin links inside `.main-content` (excluding downloads, new-tab links, and modified clicks), then uses `fetch()` to request HTML. It validates same-origin response URLs, HTML content type, and required page regions before replacing the main content and usage meter. It retains open disclosure IDs and scroll position during main-content swaps, updates the display-setting classes, and leaves Home/Archive/Settings header navigation as full-page navigation because it sits outside `.main-content`. In-page swaps do not update the address bar or browser history. Forms and links marked outside the interceptor retain normal browser behavior. Python still parses inputs, applies settings and archive changes, runs jobs and AI, and renders every returned HTML page; JavaScript only transports and swaps those pages, displays request status, and polls progress. Navigation icons retain text labels; Home also presents a three-step workflow and grouped task areas. Stronger division lines clarify page sections. The missing-package startup page links local CSS directly and has no script. Static CSS, font, and icon files are served by Flask; no runtime third-party font or image request is made. No dedicated accessibility or localization layer is included, as requested. Titles from YouTube remain source text and may contain Unicode.

## Visual system and minimal copy

The current design uses a text-only `P. 1` masthead, white page, black serif headings, small sans navigation, a restrained red accent, generous blank space, and stronger horizontal division rules. Home, Archive, Settings, results, and notices share one background. Header navigation replaced the sidebar. Search fields and the preference editor are defined by bottom or horizontal rules; there are no cards, floating windows, side panels, or shadows. A local black-and-white navigation sprite is used; no remote imagery is requested. The fixed session meter remains plain text on white at the bottom left of every running page. Source titles and summaries remain visible as content.

The interface uses the locally bundled Newsreader font for reading, with system fallbacks, and a locally bundled black-and-white engraved navigation sprite. The stylesheet is linked from each running page's head and from the startup failure page; a missing CSS file would leave the HTML readable but unstyled. The home screen groups the three steps—open a link, choose videos, read and ask—and the secondary-page guide stylesheet gives Archive and Settings task-oriented grouping. The design takes editorial patterns from The Atlantic while retaining PageOne's own name and controls.

At desktop widths, the page expands toward 2,200 pixels with proportionate side margins. At 700 pixels and below, the text navigation and masthead share one line; at 380 pixels and below, the URL control stacks to preserve its full value. Vertical space uses `dvh`; content may scroll on short viewports. Settings persist interface scale (`compact`, `standard`, `large`, `extra_large`) and reading width (`wide`, `focused`) in the version-2 archive. CSS maps those settings to body classes: the base font factor is 1, scale factors are .9, 1.15, and 1.3 for the nonstandard sizes, and focused width caps the overall shell at 1,500 pixels (wide: 2,200) while narrowing summary prose from 76ch to 64ch. The settings editor uses a two-column desktop layout and stacks below 900 pixels. Archive and Settings headings include short captions that explain each page's purpose. Playlist result lists use two columns at standard desktop widths and three at widths of at least 1,700 pixels; the check circle is 33 pixels at desktop widths and shrinks at narrow breakpoints. Summary results retain their existing grid cell when opened. On wide viewports the answer dock sits beside the active page while the list remains visible; on narrow screens it stacks below. At 520 pixels and below, the compact three-step guide and selection actions precede source search/sort; the sticky action bar keeps Summarize visible while scrolling. The footer meter has only a division line and the same white background. Error routes and startup failure show a ruled inline notice with an ordinary navigation link.

## Runtime flow

1. Home accepts a URL. `parse_youtube_url()` requires HTTPS, an exact host from the allowlist, and a valid video or playlist ID. A URL containing both IDs asks which source to use before extraction. The optional destination is validated server-side. A video link or a playlist containing exactly one video is added to that list; a multi-video playlist always creates or updates its own archive list and ignores the destination. A Home checkbox explicitly authorizes replacing saved playlist summaries on a repeat check.
2. An inspection job calls `fetch_source()`. Flat playlist metadata uses the same `yt-dlp` approach represented by the existing `apiTests/` experiments. Valid video IDs and titles are saved in original order before any summary is requested. Date and author may be `Unknown`.
3. The inspection job sends batches of at most 80 title strings to `label_video_titles()`. The JSON input contains only the titles: it does not contain transcript text, summaries, IDs, or playlist content beyond those titles. The model returns one label per title. Generic or placeholder-only titles such as `Welcome`, `The Journey`, `Video 3`, `Lecture 2`, and `Untitled` are forced to `Other` by local validation. The word check preserves Unicode title letters. Missing or malformed topic output falls back to `Other` for that batch and shows a warning.
4. The source page lists every valid title and links each title to its YouTube video. Users may search title text and select all, none, or individual rows. Each playlist order, publish date, author, topic, or title sort choice is its own submit button. A source shows 48 matched titles per page; previous/next posts retain checked IDs from other pages in hidden fields, and filtering and sorting return to page 1. The list is arranged in two columns at desktop widths and three at 1,700 pixels and above. Its selection circle is 33 pixels at desktop widths, with smaller sizes at narrow breakpoints. Checking or unchecking a title immediately submits its same-origin form so Python can refresh the selected count. Main-content form actions use same-origin HTML fetches for an in-place update; the Home/Archive/Settings header links still do full-page navigation. If source lookup fails, the job retains the validated source URL, selected kind, target list, and replacement choice in memory; its failure page offers Try again by reposting that saved request without a full-page navigation.
5. A summary job runs sequentially in a daemon thread. Existing summaries are linked by video ID and reused unless the user checks “Re-summarize.” For new or refreshed summaries, the app fetches English captions, collects the title, transcript, and current preference, then splits work into sequential in-process AI request batches. `split_summary_batches()` caps each batch at 12 videos and approximately 200,000 characters, counting title, transcript, video ID, and 200 characters of per-row overhead; this estimate excludes the shared preference and fixed prompt/schema overhead. An individual oversized row occupies its own batch. This is application-side grouping through the normal Responses create endpoint, not OpenAI's asynchronous Batch API. Each request contains one shared preference plus rows with `video_id`, `video_title`, and `transcript`; its strict output must return one nonblank summary for exactly each requested ID. A malformed or failed request marks all videos in that request batch failed, while other batches continue; successfully validated rows are saved individually, so a save error affects only that video. Transcripts are temporary and are not written to the archive or log. A repeat playlist inspection compares video IDs with the last fetched snapshot. By default it summarizes only newly found IDs and keeps old text; the Home replacement checkbox summarizes all current playlist IDs and overwrites their saved text. The General setting can disable automatic new-ID summaries. An initial playlist inspection still shows the title-selection page before summaries. New or removed remote rows reconcile with the playlist list by ID; deliberate manual list additions and removals survive that reconciliation.
6. Summary results are collapsed `<details>` rows with a server-side GET search across title, topic, and summary text. Each row can accept a follow-up question. Its POST immediately renders a loading page, then a background job fetches captions and sends only that video’s title, transcript, saved summary, recent eight Q&A turns, and current question. The local request script follows same-origin progress URLs from the HTML refresh metadata at two-second intervals and swaps each server-rendered response. Follow-up answers and individual video retry results use a shared answer dock, keeping the current playlist or archive list visible. A failed chat response keeps the original question in its retry form. `/retry-video/<source_key>/<video_id>` starts a summary job for only that video ID; it does not re-run the rest of a failed batch. Only the question and answer are saved in JSON.
7. Archive groups playlist summaries, custom summary lists, and single-video summaries. It filters list and video titles, creates empty named lists, and shows the resolved JSON path. A list page offers copy and move to another list; these alter membership without duplicating a canonical summary. A Home video sent directly to a list appears in that list rather than in the Singles group. Confirmed list deletion keeps video summaries; confirmed video-summary deletion removes that summary, its chat, and its list memberships. A saved summary with no list becomes a single-video archive entry. Settings show the error-log path and save the reusable summary preference, default playlist sort, archive sort, and automatic new-video behavior. The summary preference default is “Write a concise academic summary in coherent paragraphs. Explain the central thesis, key arguments, evidence, and limitations.”
8. Home's saved-work selector resolves one saved entry or video. **Choose videos** opens its saved detail so the user can change the selection; **Retry missing** reuses the saved source snapshot and skips completed summaries. The Archive index lets the user check entries and submit **Summarize selected** or **Retry missing**; the backend resolves current saved sources, deduplicates video IDs across entries, and builds a job snapshot rather than fabricating sources in the archive. Archive detail lets the user select specific videos or all currently matching filtered rows, summarize them, retry only missing summaries, copy/move list membership, or delete selected summaries after explicit confirmation. Replacement is honored only for **Summarize selected** when its checkbox is set. The individual **Summarize again** button sends the explicit replacement flag for that one saved video. Multi-entry jobs are labelled as a selection and do not pretend to be a playlist source.

Job progress exists only in memory. The server-rendered HTML includes a two-second refresh target while a job is pending; `local_requests.js` follows that same-origin target with GET fetches and swaps the returned HTML without a document navigation. Terminal jobs render a result or an inline notice. A pending chat job also holds its question in process memory until completion or restart. Restarting the process loses active job state, but summaries and completed Q&A written before restart remain saved.

## AI contracts and prompt-injection measures

All three AI actions use `gpt-6-luna`, `reasoning.effort="high"`, `tools=[]`, and `store=False`. The OpenAI client sets `max_retries=0`; the application sends each bounded request once and logs its failure by exception class. There is no automatic retry for connection, timeout, rate-limit, server, authentication, or response-validation failures. A user can explicitly retry through the interface. Large selections can still split into separate bounded requests. Failed calls without usage are marked unreported; response usage is recorded before output parsing, including when validation later fails.

| Action | Model input | Strict output contract |
| --- | --- | --- |
| Topic labels | A JSON object with an ordered array of video title strings only. | `{"topics": [string, ...]}` with one concise English label per title; weak titles become `Other`. |
| Summary batch | One preference string and an ordered array of `{video_id, video_title, transcript}` rows; at most 12 rows and about 200,000 estimated characters per request. | `{"summaries": [{"video_id": string, "summary": string}, ...]}` with one nonblank summary per requested ID, no duplicate or extra IDs. |
| Follow-up | Current video title, English transcript, saved summary, last eight Q&A turns, current question. | `{"answer": string}` with nonblank prose. |

Injection defenses in the implementation are layered:

1. Prompt instructions identify titles, preferences, transcripts, saved summaries, and questions as untrusted content. They direct the model to ignore instructions embedded in those values and to answer from the supplied source only.
2. Request data is serialized as JSON values and passed separately from the fixed `instructions` string. Topic requests contain title strings only; the classifier cannot infer from or receive a transcript.
3. `tools=[]` gives the model no browser, network, filesystem, or application actions. The app does not execute model output.
4. Strict structured-output schemas and Python validation reject missing, malformed, blank, or wrong-count results; Jinja autoescaping renders output as text rather than trusted markup.
5. Independently, YouTube URLs are allowlisted and normalized before extraction, and the app only binds to loopback.

These controls reduce the attack surface; no prompt can guarantee that a model will resist every jailbreak or produce factually correct text. Topic labels are generated text, not trusted categories. Summaries are reading aids, not verified quotations or citations. `store=False` disables stored Response state but does not promise zero retention under every OpenAI account or abuse-monitoring setting.

## Usage and USD cost meter

The fixed bottom-left page meter spells out the current browser session’s total, input, cached input, cache-write, output, and thinking token counts, AI call count, and known USD cost. If accounting is partial, it displays counts of unreported, unpriced, and incomplete-detail calls. Cached-input, cache-write, and thinking counts are subsets and are not added again to total tokens. One summary-batch request can summarize up to 12 videos, so API-call count is not a video count. The meter reflects reported usage, not an invoice.

As rechecked against the [official OpenAI API pricing page](https://developers.openai.com/api/docs/pricing/), [GPT-6 Luna model page](https://developers.openai.com/api/docs/models/gpt-6-luna), and [prompt-caching guide](https://developers.openai.com/api/docs/guides/prompt-caching) on 2026-11-03, GPT-6 Luna Standard rates are $0.10 per million ordinary input tokens, $0.01 per million cached input tokens, $0.125 per million 30-minute cache-write tokens, $0.25 per million 12-hour cache-write tokens, and $0.50 per million output tokens. The implementation uses exact integer units of 1/1,000,000,000 USD per token, then rounds the total to eight decimal places for display:

```text
uncached_input = input_tokens - cached_tokens - cache_write_tokens
cost = uncached_input × $0.10 / 1,000,000
     + cached_tokens × $0.01 / 1,000,000
     + cache_write_30m_tokens × $0.125 / 1,000,000
     + cache_write_12h_tokens × $0.25 / 1,000,000
     + output_tokens × $0.50 / 1,000,000
if input_tokens > 272,000 for a call:
    double that call's input, cached-input, and cache-write cost
    multiply that call's output cost by 1.5
```

The Responses usage object reports ordinary, cached, and cache-write input tokens within `input_tokens`, and reasoning tokens within `output_tokens`. PageOne parses `input_tokens_details.cached_tokens`, `input_tokens_details.cache_write_tokens`, the `ttl_30m_tokens` and `ttl_12h_tokens` write details, and `output_tokens_details.reasoning_tokens`. Subsets are displayed separately but counted once: total tokens are input plus output; cache writes and reasoning are not added again. Total is recomputed from valid input/output values if the supplied total is malformed, and the display marks that breakdown partial. A cache-write total is priced only when the 30-minute and 12-hour token details are valid and sum to that total; a missing or inconsistent breakdown makes the call unpriced and increments the partial-usage count.

The ledger is keyed by a random Flask browser-session identifier, lives only in RAM, is not written to the archive, evicts sessions after 24 hours idle, is capped at 1,000 tracked sessions, and clears on process restart. The Flask session cookie is not permanent. Missing usage is counted as an unreported attempt. If cached-input or cache-write detail is missing or invalid, input/output totals remain visible but that call is excluded from known cost and counted as unpriced. Missing reasoning detail or a total-token mismatch is marked as incomplete detail; it does not prevent pricing when the required input/cache/output rates are complete.

Displayed cost includes the usage components and rates parsed by PageOne, using the standard processing tier and the model page's over-272K-input multiplier; it is not a provider invoice. OpenAI documents implicit prompt-cache handling and 30-minute cache writes as the default for supported Responses requests. PageOne does not request extended 12-hour retention or a nonstandard processing tier. Account-level adjustments are outside this meter. Review the [prompt caching guide](https://developers.openai.com/api/docs/guides/prompt-caching) and [Responses API reference](https://developers.openai.com/api/reference/resources/responses/methods/create) when the SDK usage contract changes.

## Source and network policy

Allowed source hosts are `youtube.com`, `www.youtube.com`, `m.youtube.com`, `music.youtube.com`, and `youtu.be`, over HTTPS only. The code extracts IDs then constructs its own canonical watch or playlist URL; it does not fetch arbitrary user-supplied URLs. It tries `yt-dlp` first for flat metadata and English JSON3 subtitles/automatic captions; if lookup fails or yields unusable data, it falls back to `pytubefix` for public metadata or English captions. Transcript text is capped at 100,000 characters. No video or audio file is requested. There is no cookie jar, account sign-in, or access-control bypass. Separately, browser JavaScript may issue requests only to the app's same origin; source extraction and OpenAI traffic remain Python-side. The declared `pytubefix` dependency is bounded to `>=11.2.1,<12`.

This is not the official YouTube Data API. The [YouTube Terms](https://www.youtube.com/t/terms) and [official playlist-items API reference](https://developers.google.com/youtube/v3/docs/playlistItems/list) document the platform’s terms and an approved API route. The app uses `yt-dlp` first and the third-party `pytubefix` package as a fallback; extraction behavior, service availability, applicable terms, and legal permissions are not guaranteed. Review those conditions before broader use. Private, age-restricted, unavailable, or captionless content can fail. Flat metadata can omit author or publish date.

## Storage, privacy, and security boundary

The version-2 JSON archive stores summary preferences, five general settings (`default_playlist_sort`, `archive_sort`, `auto_summarize_new`, `interface_scale`, and `reading_width`), source metadata and title topics, summaries, timestamps, source links, chat questions/answers, and `summary_lists`. Its default path is `user data/userdata.json` beside the app; `PAGEONE_DATA_DIR` can set a different containing directory. The default rotating log is `user data/error.log`. With the default path, startup copies legacy `instance/pageone.json` and `instance/pageone.log` into the new files without deleting the originals. When a directory is explicitly configured through `PAGEONE_DATA_DIR` or `create_app(data_directory=...)`, migration looks for legacy `pageone.json` and `pageone.log` inside that directory only; it does not pull files from the app's `instance/` folder. The `archive-migration.json` receipt records the source fingerprint and target name; it distinguishes the preserved source from later destination edits. If the source/destination state cannot be verified, startup keeps both and reports the issue instead of overwriting either. A list has a stable ID, title, kind (`playlist` or `custom`), timestamps, and ordered unique video IDs. Playlist list IDs equal their source keys; custom IDs use random UUIDs. A video source has an `archive_as_single` flag when Home sends it into a list, preventing a duplicate Singles entry while its list exists. Summaries remain canonical by video ID. A valid version-1 archive is upgraded in memory when read, creating playlist lists from its saved source snapshots and adding default settings; its disk bytes are not changed until the next successful write. It does not store transcripts, API request/response bodies, or token usage. The file is readable, unencrypted JSON; protect it and the device account. The archive is written through a temporary sibling file, `fsync`, and atomic replacement under a process-local lock. If its JSON is malformed, the store refuses to overwrite it; back it up before manual repair. This lock does not coordinate multiple processes.

The app checks loopback host and client addresses, validates same-origin writes when an Origin header is present, and checks a session CSRF token on every form write. Response headers allow same-origin scripts and stylesheets, disallow framing, restrict base URLs and form destinations to self, disable caching, and prevent MIME sniffing. Local fetches send same-origin credentials and reject response redirects that leave the app origin. `DOMParser` parses the server response into a separate HTML document, after which the script clones only the server-rendered main-content and meter regions into the active page. MDN documents that parsed HTML is initially inert but is not thereby sanitized; scripts or event handlers may act if unsafe nodes are inserted into the visible document. PageOne's implementation choice is to accept only same-origin Flask-generated pages, where untrusted title/model text is escaped by Jinja, and it does not import arbitrary external HTML. This narrows the source of inserted markup but is not a general-purpose HTML sanitizer. Job progress routes check the owning browser-session ID before returning job details; a different session receives 403. The process is not hardened for remote exposure, reverse proxies, hostile local multi-user access, or shared writable folders. Do not bind to `0.0.0.0` or expose port 5000.

The `/archive/actions` route accepts only its enumerated action names, reads entry/video IDs from the current archive, validates selections and destination lists, and uses CSRF-protected POSTs. Summary deletion requires the explicit confirmation checkbox. Client-side selection checkboxes may sit outside the bulk form but use the HTML `form` attribute to associate with it. `local_requests.js` builds `FormData(form, submitter)` so the clicked button's action name/value is sent with the checked controls; MDN documents this form association and submitter behavior. The index and detail controls share a template, but their available operations differ: membership transfers and deletion are detail-only.

The OpenAI API receives the minimum current-video context for each action plus its task-specific user text. The configured `error.log` is a rotating 1 MB log with three backups; it records event names and exception class names, not transcript text, credentials, request bodies, or model output. A network failure can occur after the provider accepted a request, so that attempt may be billable even if usage is unavailable; the meter marks it unreported.

## Failure behavior and diagnosis

`run.py` checks for Flask, OpenAI, and at least one extractor (yt-dlp or pytubefix) before importing the app. If a package is missing or import initialization fails, it writes a concise cause to the launch terminal and configured `error.log`, then serves `templates/startup_error.html` on loopback using Python's standard-library HTTP server. The static page says only that PageOne cannot start, shows the script-free inline notice, and offers Retry. It exposes only the page and CSS; no directory listing. `python app.py` bypasses this preflight, so `python run.py` is the supported end-user command. If the data folder is unwritable or the port cannot bind, the terminal still reports the failure; a browser notice cannot be served without an available loopback port.

After launch, `configure_safe_logging()` writes event names and exception class names to both a rotating local file and stderr. An API failure records its exception class once in the request wrapper; the job may also record its own failure event. No automatic retry is scheduled. Raw provider messages, request bodies, transcripts, credentials, and model output are omitted. Flask routes convert predictable connection, missing-key, missing-package, source, and unexpected failures into short product notices. The notice appears before page content and Continue performs a normal GET. A failed source lookup retains the validated request values for an inline Try again form. A failed title-topic call retains the title list with `Other` labels and an inline warning; a summary batch retains successful notes and displays failures after its job finishes. Unexpected route errors are handled before Flask's default traceback page. The running app loads the visual scroll helper and same-origin request script described above; the startup failure page does not.

- Blank, insecure, invalid-ID, and lookalike-host links fail before extraction. Mixed video/playlist links ask which source to use.
- YouTube metadata and caption lookup tries `yt-dlp`, then falls back to `pytubefix`; if both fail, a safe source notice appears. Failed batch videos are listed while remaining selections continue.
- Missing or offline OpenAI access, empty content, and malformed model output produce safe notices. Each bounded model request makes one API attempt with SDK retries disabled; a failed provider call may be billable even when usage is unavailable, and that attempt's usage state is recorded once. Large title or summary work may be divided into multiple bounded requests. The user can retry an individual failed summary through the answer dock; that route submits only the one video's ID. A failed chat answer keeps the question in the answer dock's Try again form. Since batch output validation is all-or-nothing for a request, a malformed reply can fail up to 12 video summaries together.
- A malformed archive is left untouched. Back it up and inspect a copy before repair.
- A restart loses active jobs. Already saved summaries are reused by video ID unless refreshed.
- A failed repeat fetch leaves the prior source and list intact. An AI failure while summarizing newly found videos leaves successful notes and the list in place and shows a warning.
- Invalid, missing, or same-list transfer targets are rejected. Destructive list and summary actions require a confirmation checkbox and a CSRF-protected POST; list deletion never silently deletes the canonical summaries.

## Ownership, maintenance, and acceptance

The local operator owns the API key, archive backups, and update policy. Keep the unit suite free of external network requests. Before dependency changes, run compilation, fake-client tests, browser checks, and the supported `run.py` CLI smoke; run live diagnostics separately and identify quota use. Update prompts, schemas, output normalization, cost constants, visual assets, startup behavior, and this handoff together when contracts change.
